# Deploy Shielded on Dokploy

Create a Dokploy **Application** from this repository and its `main` branch. Choose the Dockerfile build type with the path `Dockerfile.dokploy`. The image downloads the genesis-4 proving keys from the GitHub release named in `Dockerfile.dokploy` (the `SHIELDED_ROLLUP_KEYS_URL` build argument) and keeps each file only if it matches `rollup-keys/genesis-4.json`. It also downloads the pinned rapidsnark prover release, checks its SHA-256, and builds the Arkade VM bridge and the web app, then starts `src/server.ts`. The host never runs a key setup.

Add the variables from [`dokploy.env.example`](../dokploy.env.example) to the runtime environment. Only Mutinynet is supported. Read [FEE-WALLET.md](FEE-WALLET.md) before setting the deposit fee variables.

Use a single-node host. In **Advanced → Volumes/Mounts**, mount one persistent volume at `/data` and set the container port to `8792`. Keep one replica: the pool journal allows a single writer. The default Swarm update order works: a replacement reports healthy while it waits for the previous container to release the pool, then takes over. Keep the volume across updates. It holds the operator keys, the proving keys and the pool journal; losing it loses the pool. It also keeps a verified copy of the current native app release under `native-releases/` (about 500 MB, briefly twice that while a new release replaces it); the download page serves that copy and falls back to GitHub until it is complete.

On first start the service copies those keys onto the volume and verifies them. It then shows an operator funding address in `/api/rollup/status`. Send at least 2,000 sats there and the service creates the pool.

For the domain, point an A record at the Dokploy server. In the application's **Domains** settings, route the hostname to port `8792` over HTTP and enable HTTPS. The wallet is at `https://HOSTNAME/wallet` and the health check at `/health`. Do not expose port `8792` directly; Dokploy's proxy handles public traffic.

Pushes to `main` deploy automatically and do not wait for GitHub Actions. Confirm a deploy by the bundle hash the site serves, not by Dokploy's status.

## App cache

The browser wallet runs from a service worker cache. Worker registrations revalidate `/sw.js` without using the HTTP cache; an installed version still waits for the user to tap **Update** in the wallet or close every tab using the old version. Public home and download navigations fetch fresh HTML, using the cached page only when offline. Public pages do not show an app-update prompt. The `/download` route also bypasses older workers that cached the home page. Two build arguments change activation. Set them in **Environment → Build Time Arguments**, not in the runtime environment, and redeploy. While either is on, the build log prints a `[plugin app-cache]` line naming it.

**Forcing.** `SHIELDED_APP_CACHE_FORCE=1` is only for a release that crashes before the Update bar can show: a browser installs the forced build and reloads its tabs without asking. Set it as a build argument, deploy, then purge `/sw.js` in Cloudflare. Unset it before the next push to `main` deploys, or every later deploy skips consent too.

**Rollback.** A forced build of the last good commit. If that commit predates the app cache, its build has no worker and answers `/sw.js` with a 404, which leaves the old worker in control. Deploy a cache-enabled build with `SHIELDED_APP_CACHE_OFF=1` first, keep it deployed until affected browsers have fetched it (at least a day, plus however long their users take to visit), and only then roll back to the older commit.

**Removal.** `SHIELDED_APP_CACHE_OFF=1` ships a worker that deletes the app's caches, unregisters itself and reloads the tabs it controlled, and the page stops registering one. A browser removes its copy the next time it checks `/sw.js`, so keep the argument set for as long as the cache should stay off.

**Wallet reloads stay on the installed version.** An open or returning wallet keeps its version until the user taps Update or every tab using it has closed. Server changes must remain compatible with those clients. Public `/` and `/download` pages use the current HTML without replacing the pinned wallet shell; no wallet storage needs clearing.

## Oblivious HTTP gateway

The pool server can open Oblivious HTTP (RFC 9458) requests, so a wallet reaches the pool, arkd, the Arkade indexer and Esplora through a relay that sees its address but not what it asks for. The gateway is off until `SHIELDED_OHTTP_KEY` is set. While it is off, `GET /api/rollup/ohttp-keys` and `POST /api/rollup/ohttp` answer 404 once the pool has opened. Before that they get the pool's 503 instead: "The rollup pool is starting.", or "The rollup pool is not open yet" while the pool is not open, for example while a rollout waits for the volume lock.

**Turn it on.** For testing only for now. Production use waits for three things: a measurement of CPU and memory under a flood on the real host, a way to rotate the key without stranding wallets, and replay protection that survives a restart. The Nostr carrier lets anyone reach the gateway through public relays, so there is no list of callers to hold it to. Every event a listed relay forwards, a flooder's included, costs the pool's main thread work as it arrives, and every answer costs signing and bandwidth going out. Rotation is a hard cut (see **Rotate**), so before any wallet pins a config, the gateway needs to hold the old and new keys together, or wallets need a stale-key signal they act on. A new process starts with an empty replay register, so a copied request dated just before it started can run once more (see **Start and stop**); production needs that register kept across restarts, or every request it forwards made safe to run twice. Run `npm run ohttp:keygen -- <file>` on a trusted machine. It writes the line `SHIELDED_OHTTP_KEY=<key id>:<private key>` to `<file>` (mode 0600, which holds on Linux and macOS but not on Windows, and it refuses to overwrite an existing file) and prints only the key id, the config and the gateway's Nostr key (`nostr: <hex>`), which are public. Paste the line into the application's runtime **Environment**, delete the file and redeploy. Never put the key in a command line, a log, a chat or the repository. Publish the printed config and Nostr key: the wallet build that uses the gateway pins both.

**Verify.** The start log shows `Oblivious HTTP gateway on (key id N, Nostr 3c857963…, 6 relays, HTTP route off).`, with the key id and the first 8 characters of the Nostr key the tool printed. `GET /api/rollup/ohttp-keys` then returns content type `application/ohttp-keys`, and its bytes equal the printed config. This prints the content type and the bytes in the tool's base64url encoding:

```
node -e "fetch(process.argv[1]).then(async r=>console.log(r.headers.get('content-type'),Buffer.from(await r.arrayBuffer()).toString('base64url')))" https://HOSTNAME/api/rollup/ohttp-keys
```

This proves the key and the config. It does not prove the gateway's hop to the pool or to the upstreams; only a sealed request does. The response is cacheable for an hour, so a cache in front can show the old config for that long after a rotation.

**Settings.** Runtime environment variables:

- `SHIELDED_OHTTP_KEY`: the private key as `<key id>:<base64url key>`. A secret. Unset or empty leaves the gateway off.
- `SHIELDED_OHTTP_RATE`: requests per second across all callers, from the Nostr carrier and the HTTP route alike. Default 20.
- `SHIELDED_NOSTR_RELAYS`: the `wss://` relays the Nostr carrier listens on, at most 12, separated by commas. Unset or blank uses the six relays under **Nostr carrier**.
- `SHIELDED_OHTTP_HTTP`: `1` mounts `POST /api/rollup/ohttp`, the route an HTTP relay uses. Anything else leaves it off, and sealed requests arrive only over Nostr.
- `SHIELDED_PUBLIC_ORIGIN`: the origin a wallet names for the pool inside a sealed request. Default `https://shielded.mutinynet.arkade.sh`. Set it on any other domain.
- `SHIELDED_ESPLORA_URL`: the Esplora base URL. Default `https://mempool.mutinynet.arkade.sh/api`.
- `SHIELDED_ARK_URL` and `SHIELDED_INDEXER_URL`: already used by the pool, and the gateway forwards to the same servers. The indexer defaults to the arkd URL. Both are bare origins, with no path, as the pool already requires.

A malformed key, a rate that is not a whole number of at least 1, an upstream URL that is not `https` (or an arkd or indexer URL that is not a bare origin), a relay list with an entry that is not a `wss://` URL or more than 12 relays, a `PORT` that is not a fixed number, or a `HOST` other than `0.0.0.0` or `127.0.0.1` stops the server at start, like any other bad setting. The error never prints the key. While there is no key, the other checks do not run, and the rate, the public origin, the Esplora URL, the relay list and the HTTP route setting are ignored.

**What it forwards.** Only `GET` and `POST`, and only to these:

- the pool, for paths under `/api/rollup/` other than the gateway's own two, reached at `http://127.0.0.1:$PORT`. The image sets `HOST=0.0.0.0` and `PORT=8792`: do not set `HOST` in Dokploy, where `127.0.0.1` would cut off the proxy, and keep `PORT` a fixed number;
- arkd under `/v1/` and the indexer under `/v1/indexer/`, each on a bare origin, and Esplora under the path of its base URL.

If the pool's public origin is also an upstream's, only `/api/rollup/` paths on it go to the pool; every other path on it is checked against the upstream list. Event streams are refused. The gateway's pool requests carry a token it makes at start. The pool lets only loopback requests with that token skip its per-address limit on submissions, because every sealed request would otherwise count against 127.0.0.1. The gateway's own budget applies instead.

**What the shared budget costs.** One holder of the public key config can submit at the whole `SHIELDED_OHTTP_RATE`: 20 a second by default, about 1,200 a minute, against 60 a minute per address when calling the pool directly. Each submission costs a Groth16 check. The budget is shared and first come, first served, so that caller crowds out every other sealed caller, reads included. It can also push direct `/spends` requests to a 503 "busy", because the cap on spends being checked at once (8) is shared by everyone. To cut it, lower `SHIELDED_OHTTP_RATE` or unset the key.

**Limits and logs.** A request over 1 MiB gets an outer 413, and one still uploading after 30 seconds is cut off. A response over 4 MiB, or an upstream that takes over 30 seconds, comes back as an inner 502 or 504. Whatever the upstream or the reading client does, the connection is cut after 90 seconds, three times that deadline, so no request holds a slot longer. A sealed request carries an inner `X-Date` rounded to the nearest 30 seconds (not `Date`, which a browser strips). One dated more than 90 seconds from the gateway's clock, or more than 15 seconds before the gateway's start, is refused like a repeat: an outer 400 on the HTTP route, and no answer over Nostr. The start is when the Nostr listener starts (see **Start and stop**), and the process start until then. Of the client's headers only the content type, `Accept` and `X-Digest` cross to the upstream, and of the upstream's only the content type, the cache control and `Retry-After`, so a sealed client can wait as told. All callers share one budget, `SHIELDED_OHTTP_RATE` a second and 32 requests in flight; past it the gateway answers an outer 429 or 503 with `Retry-After: 1`. It logs counts by kind, such as `[ohttp] forwarded 120, busy 3`, at most once a minute, and never a target or a body.

**Rotate.** The gateway holds one key at a time. Run `ohttp:keygen` again. It picks the key id at random, so if it prints the id already in use, run it again. Replace the `SHIELDED_OHTTP_KEY` line, redeploy and publish the new config. The wallet build that uses the gateway pins the config, so a rotation also needs a new app build. Until a client has the new config, its requests are sealed to the old key id, and the gateway answers them with an outer 400.

**Roll back.** Unset `SHIELDED_OHTTP_KEY` and redeploy. The start log then says `Oblivious HTTP gateway off.`, the Nostr listener does not start and, once the pool has opened, both HTTP paths answer 404.

**The HTTP relay.** With `SHIELDED_OHTTP_HTTP=1` the gateway only opens requests, and a separate relay carries them. It must be run by someone other than us or Arkade: the relay sees who is asking and the gateway sees what, so one operator for both would see both. It must not sit on Cloudflare, which already fronts this domain. It must apply a per-client rate limit, because it is the only hop that sees callers. It forwards each sealed request as `POST /api/rollup/ohttp` with content type `message/ohttp-req`, and it adds the CORS headers for the wallet's origin. The gateway sends none, because the browser talks only to the relay.

### Nostr carrier

A wallet can also send its sealed request inside a Nostr event, so no relay of ours or Arkade's has to carry it. The listener subscribes to each relay for kind 21470 events addressed to the gateway's Nostr key and opens each through the same gateway as the HTTP route, with the same rate, in-flight cap, repeat check and date window. Requests are grouped by the hash of their sealed bytes, so every copy of a request, from any relay and from anyone, shares one run. The listener publishes the sealed answer as kind 21471 events signed by that key, to every relay that delivered a copy. A copy from a new relay within 30 seconds of the answer gets the answer re-published there; the listener keeps answers for this up to 16 MiB in total. A request is one event carrying at most 32 KiB of sealed bytes, and an answer is a set of events carrying 32 KiB each: the format allows 32, and the listener sends at most 8. In base64 with the event's fields that is about 44 kB an event, so a relay needs an event size limit above that. The listener asks the gateway for no more than 241,644 bytes (about 236 KiB) of upstream body, the most whose sealed answer fits 8 events whatever headers come with it, so a larger upstream answer comes back as an inner 502. That guarantee assumes Node's default 16 KiB limit on response headers. With a larger `--max-http-header-size`, for example through `NODE_OPTIONS`, an answer can take more than 8 events, though never more than 32. When the gateway is busy the listener publishes a status event instead (503 over 32 requests in flight, 429 over the rate, each with a retry delay of 1 second and the id of the request event it answers) and runs nothing, so the wallet may send again. Answer events, re-published ones included, draw on an outbound budget of 64 publications a second, one event to one relay each. An admitted answer is published whole even if that puts the budget into debt, and a new request that finds the budget spent gets a 503 status before it runs. Answers to requests that ran always go out, so the budget can fall into debt by the answers to the 32 requests in flight, at up to 8 events to each of up to 12 relays that carried a copy (3,072 events), plus re-publishes of answers signed in the last 30 seconds to the 11 other relays: about 4,200 events if all are full-size, which the 16 MiB cache bounds, about 6,600 if all are small, which the default `SHIELDED_OHTTP_RATE` of 20 a second bounds, and about 10,600 for the worst mix, small answers beside two-event answers just over one chunk. That is about 14,000 events at worst, and every new request is then shed with a 503 for up to about 3.5 minutes while the budget repays them at 64 a second. Fewer relays in `SHIELDED_NOSTR_RELAYS`, or a lower `SHIELDED_OHTTP_RATE`, lowers that ceiling; the in-flight cap of 32 is fixed. At most 5 status events go out a second: past that the listener publishes nothing and counts `status-capped`, and the wallet's attempt times out instead, so a GET is sent again and a POST ends `outcome-unknown`. A request the gateway cannot open (not sealed to this key, a repeat, or dated outside the window) gets no answer, and neither does any event that is not a valid request.

**Relays.** `SHIELDED_NOSTR_RELAYS` is a comma-separated list of `wss://` URLs. Unset or blank, it is `wss://relay.snort.social`, `wss://nostr.oxtr.dev`, `wss://nostr.data.haus`, `wss://nostr.sathoarder.com`, `wss://relay.mostro.network` and `wss://nostr-01.yakihonne.com`, none of which sat behind Cloudflare when probed on 2026-11-10. Choose relays by the same rule as the HTTP relay: a relay sees who is publishing and the gateway sees what, so no relay may be run by us or Arkade (never `wss://nostr.arkade.sh`), and none may sit behind Cloudflare, which already fronts this domain. Every relay listed must also echo an event to the connection that published it, and its message limit must be 512 KiB or less, as its NIP-11 `max_message_length` or a probe shows, which leaves headroom under the gateway's 1 MiB frame cap for the envelope a relay forwards an event in. The six defaults allow at most 512 KiB. A listed relay must also forward events byte for byte, without re-escaping `<`, `>`, `&`, control characters or non-ASCII characters, because re-escaping can push a forwarded event past the 1 MiB frame cap. A wallet publishes to relays from its own list. A GET that reaches only relays the gateway does not listen on loses an attempt. A POST that does loses the whole request: a relay accepted it, so the wallet never sends it again and it ends `outcome-unknown`. Keep this list equal to the wallet build's or larger.

**The key.** The gateway's Nostr key is derived from the OHTTP key (HKDF-SHA256 over the 32-byte secret, with the info `shielded-nostr-carrier-v1`), so there is no second secret to keep and a rotation changes both. `ohttp:keygen` prints its public half as `nostr: <hex>`, and the start log shows the first 8 characters. Run one instance per key: two servers with the same `SHIELDED_OHTTP_KEY` both hear every request and both answer it, so a GET gets two conflicting sets of chunks and a POST to arkd runs twice.

**Start and stop.** The listener starts once, the first time the pool has opened, and logs `Nostr carrier listening on N relays.` It closes before the pool does. While a rollout waits for the previous instance to release the volume, the new instance does not listen. It asks each relay only for requests from then on (`limit:0`, and none dated more than about a minute earlier), so a restarted instance does not run again the requests a relay still stores; a relay that ignores `limit:0` can still hand back the last minute's. The same holds when the listener resubscribes after losing a relay: requests that reached that relay during the gap are never heard. They never run, so a GET goes out again through another relay. A POST that only that relay took ends `outcome-unknown`, even though it did not run. Across a restart, the gateway refuses any request whose `X-Date` is more than 15 seconds before its listener started, and its register starts empty. The previous instance keeps answering while a rollout waits for the volume lock, so a request dated in the last 15 seconds before the new listener started, which the previous instance may already have answered, can run once more if a copy reaches the new instance within 90 seconds of its `X-Date`.

**What a relay and its readers see.** The relay sees the address of the wallet that publishes, and the event: a one-time key as author, the gateway's key in the `p` tag, a time rounded to the nearest 30 seconds and the sealed bytes. Each relay also sees the pool server's own address, which Cloudflare otherwise hides: the listener's connections to the relays go out from the server's egress address. Anyone who reads the relay sees the same events without the address, and the answers: the gateway's key as author, the hash of the sealed request (`x`) and the chunk numbers in the tags, and when. A status event carries, instead of chunk numbers, its status code, its retry delay and the id of the request event it answers. Neither learns the target or the body, which only the gateway can open. The gateway learns them but not the address, because a relay is the only path a request takes to it. Sizes show: a request's length and an answer's chunk count say roughly how much was asked and returned. Anyone who reads the relay can also copy a request's sealed bytes into an event of their own. The window, not the register of opened requests, is what bounds a replay: a copy that reaches the gateway more than 90 seconds after the original's `X-Date` gets no answer at all, and within those 90 seconds the register refuses it, except across a restart (see **Start and stop**) or once 100,000 newer requests have opened, since the register keeps only the latest 100,000. At the default 20 a second, that takes over an hour.

**Logs.** The listener logs counts by kind, such as `[nostr] answered 12, busy 1, dropped 3`, at most once a minute, and never an event, a relay or a target. `answered` and `busy` are published; `status-capped` is a status event held back because 5 went out in that second; `refused` is a request the gateway would not open; `dropped` is an event that is not a valid request; `duplicate` is another copy of a request already seen; `republished` is a cached answer sent to a relay that delivered a copy late; `failed` is an error after the request was accepted, where nothing is published because the request may have run; `unpublished` is an answer event a relay refused, timed out or could not be reached for; `lost` is a relay whose subscription closed, or that could not be reached, which the listener tries again after 30 seconds; `deaf` is a relay that did not echo the canary within 15 seconds, which the listener closed (so it counts `lost` too) and tries again after 30 seconds; `canary-refused` is a canary a relay refused with a NIP-01 prefix, such as `rate-limited:`, which is not taken for deafness, so the relay stays subscribed, unchecked until a canary goes through. The gateway's own `[ohttp]` line counts `outbound`, a request shed because the carrier's outbound budget was spent, and `stale`, a request dated outside the window. A wallet whose clock is off by more than about 75 to 105 seconds (the 90-second window, give or take the 15 seconds of rounding) has its requests counted `stale` and gets silence, so it stops syncing without saying why. Relay NOTICE messages are not printed. The listener cannot silence one thing: when a relay sends a message the Nostr library cannot parse, or an event it cannot match (a kind 21470 event with no tags, say), the library prints its own warning to stderr, `[nostr] relay <url> error processing message:` with the error, and with the event itself in the second case. For a frame it cannot parse, the error is V8's, which quotes up to 10 characters of the frame on either side of the fault. A relay that does this is misbehaving; take it out of `SHIELDED_NOSTR_RELAYS`.

**Limits.** Liveness: every 30 seconds the listener sends each relay a canary, a kind 21470 event from its own key with empty content, and expects it back within 15 seconds, so a relay that keeps the socket open but stops forwarding events is closed and subscribed again. The canary also keeps open a relay that drops idle connections (one dropped them after 60 seconds). A frame over 1 MiB closes the connection, a connection whose upgrade stalls for 10 seconds is dropped, and a relay with more than 4 MiB unsent gets no more events until it drains. Each relay message is handled on its own, so a copy of a request that arrives together with a copy the gateway sheds is opened afresh, and is answered or gets a status naming its own event. Restarting the service reopens every subscription. The status cap: under a flood, a request that was shed but not told (past the 5 a second) looks to the wallet like one that may have run.

#### The private wallet build

The browser wallet can send its requests to the pool, arkd, the Arkade indexer and Esplora through this carrier instead of calling them directly; only the page itself, the proving files and the list of native downloads still load from the site. For now this is an internal flag, for fresh test wallets only.

**Build arguments.** The app build takes four, set in **Environment → Build Time Arguments**; redeploy after changing any. The first two are build arguments only. The server also reads the last two at runtime, so they are build arguments in addition to the runtime environment, not instead of it:

- `SHIELDED_OHTTP_CONFIG`: the `config:` value `ohttp:keygen` printed.
- `SHIELDED_NOSTR_GATEWAY`: the `nostr:` value it printed.
- `SHIELDED_NOSTR_RELAYS`: the relays the wallet publishes to, separated by commas. Unset or blank uses the six defaults under **Relays**.
- `SHIELDED_PUBLIC_ORIGIN`: the pool's origin. Unset or blank uses `https://shielded.mutinynet.arkade.sh`.

A build missing either of the first two has no private transport. The build pins `SHIELDED_PUBLIC_ORIGIN` as the origin every sealed pool request names, so give it the same value as the runtime one. It pins `SHIELDED_NOSTR_RELAYS` as the relays the wallet publishes to, which must be the gateway's runtime list or part of it.

**Turn it on.** On a pinned build, `?private=1` on any page turns the transport on for that browser profile. Use it only with a fresh test wallet. A private wallet has no Lightning, no renewal, no on-chain exit and no explorer links, and it shields at most 20 coins at a time; a transaction id shows as plain text. If the transport cannot start, the page says why and the wallet stays closed. A build from before the private transport, which a rollback can return to, and a tab still running an older version from the app cache both ignore the flag and send every request direct, so tap Update before opening a page with `?private=1`. A build without both pins that sees the flag, in the URL or stored, keeps the wallet closed and says "this build has no private gateway pinned"; to open it, remove the key as under **Turn it off** and load the page without `?private=1`.

**Turn it off.** No link turns it off, so nobody can send a tester a link that quietly returns their wallet to direct requests; `?private=0` does nothing. Delete the `localStorage` key `shielded-private-transport-v1` in the browser's developer tools, or clear the site's data, then open the page without `?private=1`, which sets the key again on every load. Clearing the site's data deletes the wallet as well, so back up its recovery phrase first. If the wallet says some payments have unresolved outcomes, you can wait until that line clears before turning it off: without the transport, the wallet no longer keeps those payments' notes reserved.

**Keep the pins equal to the gateway's.** The key config and relays a build pins must match the gateway's `SHIELDED_OHTTP_KEY` and `SHIELDED_NOSTR_RELAYS`. After a rotation, a pinned build seals to the old key, and over Nostr the gateway answers that with silence, not a stale-key error, so its wallets stop syncing without saying why. At every rotation, rebuild the app with both new pins, `SHIELDED_OHTTP_CONFIG` and `SHIELDED_NOSTR_GATEWAY` (the Nostr key is derived from the OHTTP key, so it changes too), and have testers tap Update or close every tab of the site, since the app cache serves the old build until then. Keep the gateway's relay list equal to the build's or larger.
